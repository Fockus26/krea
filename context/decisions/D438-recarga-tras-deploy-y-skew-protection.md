# D438 · QA · Tras un deploy: una recarga automática por chunk o Server Action desfasados; Skew Protection de Vercel · Implemented

**Decision:** `app/error.tsx` y `app/global-error.tsx` llaman a `recargarSiEsDeploy(error)` (`lib/recarga-deploy.ts`): si el error es `ChunkLoadError` («Failed to load chunk …» de Turbopack, «Loading chunk … failed» de webpack) o `UnrecognizedActionError` / «Failed to find Server Action», hacen UNA recarga completa y guardan la hora en `sessionStorage` (`krea:recarga-deploy`); si vuelve a fallar antes de 30 s, sale la pantalla normal. Sin `sessionStorage` no recarga. El SW (D291) no cambia. En Vercel se activa **Skew Protection** (Project › Settings › Advanced › Skew Protection, con una ventana de 12 h o más): Vercel fija `NEXT_DEPLOYMENT_ID` en cada build y Next lo usa solo (`?dpl=` en los assets, recarga dura al detectar otro deploy), así que `next.config.ts` no lleva `deploymentId`.
**Why:** una pestaña abierta antes del deploy, o una página vieja servida por el SW tras `ESPERA_RED_MS`, pide chunks e ids de Server Action que ya no existen; «Reintentar» repinta con el mismo JS y vuelve a fallar. La guía de Next (`server-actions.md` › Deployment considerations) pide tratar ese error como camino de reintento con recarga.
**Discarded alternative:** `deploymentId: process.env.VERCEL_DEPLOYMENT_ID` en `next.config.ts` — sin Skew Protection, Vercel no enruta por deploy y Next solo recargaría más; con ella, Vercel ya lo pone. Recargar en cada error — un error real de servidor entraría en bucle o escondería el código `KR-500`.
