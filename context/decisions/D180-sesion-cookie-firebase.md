# D180 · Auth · Login en el navegador + cookie de sesión httpOnly del Admin SDK; proxy rápido y DAL cerca del dato · Implemented

**Decision:** `Ingresar` hace `signInWithEmailAndPassword(<cedula>@alumnos.krea.app)` con el SDK del navegador (D008) y manda el idToken a la Server Action `iniciarSesion` (`lib/acciones/sesion.ts`), que lo verifica (con revocación), exige un login de hace < 5 min y claims válidos (`sesionDeClaims`: rol, sección del estudiante, uid = cédula) y crea la cookie `__session` (5 días, `httpOnly`, `secure` en producción, `sameSite: lax`). `proxy.ts` verifica la firma de la cookie en cada ruta protegida y redirige por rol (`redireccion`, `lib/sesion.ts`); el DAL `verificarSesion`/`exigirSesion` (`lib/dal.ts`) la vuelve a verificar **con revocación** en cada página o acción con datos (W4+). Errores: los códigos de Firebase pasan por `errorIngresoDeCodigo` y nunca dicen qué campo falló; el límite de intentos es el de Firebase Auth (`auth/too-many-requests` → «bloqueado»).
**Why:** el SDK del navegador tiene que quedar con sesión para las lecturas en vivo (`onSnapshot`) y la cookie httpOnly protege las rutas en el servidor, también las estáticas (el proxy corre antes de servirlas).
**Discarded alternative:** login en el servidor con la REST de Identity Toolkit — el navegador quedaría sin sesión de Firebase para Firestore. Token en `localStorage` — prohibido.
