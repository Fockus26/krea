# D409 · API · `/api/presencia` acepta `entrega`; `usePresenciaEntrega` sondea `?entrega=` y marca con latido · Implemented

**Decision:** POST acepta `{ accion, cedula }` (como hasta ahora) **o** `{ accion, entrega }` (`zPedidoPresencia` en `lib/presencia.ts`: unión de dos objetos `strict`, así que un pedido con los dos campos, o con ninguno, es 400). El id de entrega se valida con `zIdEntrega`, el mismo patrón que `zIdDocumento` (copiado para no traer `lib/evaluar-datos` al bundle del cliente). GET sin parámetros devuelve solo las entradas de alumnos (igual que antes para la lista de Alumnos); `GET ?entrega=<id>` devuelve `{ ahora, entradas: EntradaPresencia[] }` de esa entrega (id inválido → 400). Mismo control de acceso (`accesoPresencia`, solo profesores). En el cliente, `use-presencia.ts` añade `usePresenciaEntrega(yo, entregaId)` (sondeo cada `SONDEO_MS`, reloj del servidor, reloj de vigencia de 15 s, marca + latido cada `LATIDO_MS` + `pagehide` con `sendBeacon`) y comparte el latido con `useMarcarPresencia`, que no cambia de firma. `PresenciaEvaluar` se monta en Evaluar justo tras `<ReviewHeader>` con `key={entregaId}`, solo si no es `?ver` y hay preguntas (quien solo mira no «está evaluando»).
**Why:** una sola ruta y una sola tabla para las dos presencias; el GET de Alumnos no debe traer filas que no sabe agrupar.
**Discarded alternative:** una ruta nueva `/api/presencia/entrega` — duplica sesión, acceso y `sendBeacon` para lo mismo. GET sin parámetros con todo mezclado — la lista de Alumnos tendría que filtrar en el cliente.
