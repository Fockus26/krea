# D194 · Data · Los archivos van a Backblaze B2 (API S3), no a Firebase Storage · Implemented

**Decision:** respuestas en imagen (W5) y logos de equipo (W8) en un bucket **privado** de Backblaze B2 a través de su API compatible con S3 (decisión de César, 2026-11-05: Firebase Storage exige el plan Blaze y no se paga). Cliente `aws4fetch` (SigV4, ~2,5 KB, sin dependencias) en `lib/almacen/s3.ts` con `fetch` inyectado (`crearAlmacen(config, { fetch })`: `subir`, `urlFirmada`, `borrar`); el enlace con el entorno es `lib/almacen/b2.ts` (`server-only`). Variables solo servidor: `B2_KEY_ID`, `B2_APPLICATION_KEY` (secretas), `B2_BUCKET_NAME`, `B2_ENDPOINT`, `B2_REGION`; si falta alguna no hay almacén y las acciones responden «no se pudo». La subida firma el hash real del cuerpo (no `UNSIGNED-PAYLOAD`). `firebase/storage.rules` queda cerrado tal cual; `logoPath`/`imagenPath` del modelo son claves del bucket. Actualiza la línea «Storage» de PROJECT_CONTEXT.
**Why:** sin costo (capa gratuita de B2: 10 GB y 2.500 descargas/día), API estándar, y el cliente no toca el bucket (D175).
**Discarded alternative:** `@aws-sdk/client-s3` + presigner — decenas de paquetes para tres operaciones y pide desactivar los checksums por defecto con B2. Bucket público — las respuestas de los alumnos quedarían abiertas a cualquiera con la URL.
