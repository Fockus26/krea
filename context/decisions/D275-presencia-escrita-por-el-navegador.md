# D275 · Data · Presencia al editar alumno en `presencia/{alumno}/editores/{profe}`, escrita por el navegador del profe · Implemented

**Decision:** reemplaza en parte a D175: solo `presencia/`. El diálogo «Editar alumno» escribe con el SDK del navegador `presencia/{cedulaAlumno}/editores/{cedulaProfe}` = `{ nombre, desde, latido }` (timestamps del servidor) al abrir, renueva `latido` cada 20 s (`LATIDO_MS`, `lib/presencia.ts`) y la borra al cerrar, al desmontar y en `pagehide`; si el latido no la encuentra (otra pestaña la borró, bfcache), la vuelve a crear. Reglas: leer `esProfe()` (también la consulta de grupo `editores`); crear/actualizar/borrar solo si `esProfe()` y `uid == cedulaProfe`, claves exactas (`hasOnly` + `hasAll`), `nombre` texto 1–120, `latido == request.time`, `desde == request.time` al crear (al actualizar, igual al anterior o `request.time`), cédula en la ruta. Fuera de `presencia/`, el cliente sigue sin escribir nada. Sin sesión de Firebase en el navegador (y si `tokenEnVivo` falla, D190) la presencia se apaga en silencio. Al eliminar un alumno, el Admin borra sus entradas (`borrarPresenciaAlumno`); si falla, quedan huérfanas e inofensivas.
**Why:** es efímera y no es dato de notas; una Server Action cada 20 s llamaría `refresh()` (#81) y vaciaría la caché del router, y no hay Cloud Functions (plan Spark) para limpiar.
**Discarded alternative:** Server Action con Admin para el latido — `refresh()` en cada latido o una excepción a la regla de #81. Realtime Database con `onDisconnect` — otro servicio y otras reglas para un aviso.
