# D538 · QA · El `catch` de una Server Action en un cliente deja pasar el error de deploy (`siNoEsDeploy`) · Implemented

**Decision:** `lib/recarga-deploy.ts` exporta `siNoEsDeploy<T>(red: T): (e: unknown) => T` y `relanzarSiEsDeploy(e): void`. Si el error es de deploy (`esErrorDeDeploy`: `UnrecognizedActionError`, `ChunkLoadError`…), intentan `recargarSiEsDeploy(e)` (D438) y **re-lanzan** `e` (si la marca anti-bucle impidió recargar, llega a `app/error.tsx`); cualquier otro fallo devuelve `red` (`.catch(siNoEsDeploy<ResultadoX>({ ok: false, error: "red" }))`) o sigue el `catch` normal. Se aplicó a todos los `catch` de Server Actions de `components/` y de `lib/lote.ts` / `lib/push-cliente.ts`; `analisis-ia.tsx`, que no tenía `catch`, ahora lo lleva. `tests/unit/recarga-deploy.test.ts` incluye una guarda estática que falla si en `components/` vuelve a haber un `.catch(() => ({ ok: false … }))` a pelo o un `catch` que arma `error: "red"` sin `relanzarSiEsDeploy`.
**Why:** el `catch` de cada formulario convertía el `UnrecognizedActionError` (pestaña con el build anterior tras un deploy) en «No se pudo conectar»: nunca llegaba a `app/error.tsx`, que es quien recarga (D438), y «Reintentar» repetía el mismo fallo.
**Discarded alternative:** (a) llamar a `recargarSiEsDeploy` y devolver `red` sin re-lanzar — si la recarga no ocurre (marca anti-bucle), el alumno vería «sin conexión» para siempre; (b) un wrapper alrededor de cada Server Action en el servidor — el error nace en el cliente (el id de acción no existe). Límite conocido: dentro de `startTransition(async …)` el re-lanzamiento llega al error boundary; en un manejador `async` suelto (`onSubmit`, `onClick`) React no captura el rechazo, así que ahí la salida real es la recarga y, si la marca anti-bucle la impide, queda un rechazo sin manejar (el formulario sigue en «cargando»).
