# D199 · Data · Tareas del profe: borradores a medias en `tareas`, publicar con zod y suma 20, lecturas del profe detrás de `exigirSesion("profesor")` · Implemented

**Decision:** el constructor guarda con la Server Action `guardarTarea({id, accion, tarea})` (`lib/acciones/tareas.ts`): zod (`zGuardarTarea`), autor de la sesión y **una** transacción del Admin SDK (`guardarTareaEnTransaccion`). Un borrador es un documento de `tareas` con `estado: "borrador"` que valida con `zTareaBorrador`: solo exige el título; enunciados vacíos y valores sin poner (D103) se guardan para seguir otro día. `zTareaDoc = zTarea | zTareaBorrador` lo leen el profe y, para filtrar, `tareasDeSeccion` del estudiante (que sigue sin ver borradores). «Publicar» exige título, fecha de hoy o después (día de Caracas), enunciados, valores y suma exacta de 20 (D004) y escribe `estado: "abierta"`; el premio solo se guarda si es grupal (D116). La tarea nueva recibe id automático en el primer guardado y la URL pasa a `/profe/tareas/{id}` sin volver a montar el constructor (`history.replaceState`). Las preguntas conservan su id (`q{n}`; las del seed `p{n}`). Lista, constructor y Premios leen de `lib/datos/profesor.ts` (`cache`, Admin SDK); el shell del profe sale de la sesión (como D189). Ninguna de estas escrituras mueve puntos (D007), así que no recalcula `ranking/{seccion}`.
**Why:** D175 (escrituras en el servidor) y el flujo del lienzo («Guardar borrador» con una tarea a medias); exigir `zTarea` en un borrador obligaría a borrar lo que el profe aún no escribió.
**Discarded alternative:** colección aparte para borradores — mover el documento al publicar cambiaría el id; relajar `zTarea` — el estudiante tendría que manejar valores `null` que nunca ve.
